# 當 prefill 變快，agent 反而變慢

我把 16K 冷啟動的首字延遲從 57.84 秒壓到 19.24 秒。32K 從 122.7 秒壓到 33.5 秒。
測完那兩組數字我很滿意。接著把同一份設定接上真正在寫程式的 agent，整個 session
變慢了。

慢的不是一點。

那個優化沒有 bug，它做的事情完全符合設計。我量錯的是對象。

## 看起來很明顯的瓶頸

在單機上跑 27B 等級的 MoE 模型，長 context 的痛點很好指認。使用者按下 enter 之後，
在第一個 token 吐出來以前，整段 prompt 要先被算過一遍。32K 的 prompt 要等兩分
鐘，而且這兩分鐘沒有任何東西可以遮掩。

於是 prefill 成為優化目標。兩條路我都走了：把一部分計算搬到 ANE，以及 speculative
prefill —— 用一顆 0.8B 的小模型先替 prompt 裡的 token 打分，只有分數高的那 20% 進
入完整的 attention 計算，其餘略過。超過 8192 token 的 prompt 才啟用。

## 贏了，而且贏很多

| prompt | dense | 加速後 | |
|---|---:|---:|---|
| 14.3K | 47.0 s | 11.9 s | 3.9x |
| 16K | 57.84 s | 19.24 s | 3.0x |
| 32K | 122.7 s | 33.5 s | 3.7x |

Prefill 吞吐在 16K 從 302 tok/s 到 1046 tok/s，32K 從 277 到 1112。ANE 與
speculative prefill 兩個機制在隔離的 smoke run 裡（單一常駐 engine）也不打架：
16K 同時開啟約 1328 tok/s，對照組約 300 tok/s，兩者疊加後達到理想乘積的
95-97%。

這些數字我到現在都還認。問題出在它們回答的是哪一個問題。

## 反轉

真實的 coding agent session 長這樣：第一個請求帶著系統提示、工具定義、專案脈絡，
已經是一個長 prompt。Agent 讀檔、跑指令、再問一次，第二個請求是前一個加上新的內
容。第三個再加。到第八輪，prompt 比一開始大得多，但絕大部分跟第七輪一模一樣。

這種形狀的 workload 早就有對策，叫 prefix cache：把算過的 KV 狀態存下來，下一個
請求只算新增的尾巴。它平常運作得很好。

我把 speculative prefill 打開，跑真的 agent，量每一輪的 cache 命中率：

| 輪次 | dense | sparse |
|---:|---:|---:|
| 1 | 82.2% | 88.2% |
| 2 | 94.0% | 63.9% |
| 3 | 75.6% | 51.0% |
| 4 | 98.6% | 40.7% |
| 8 | 98.1% | 27.1% |

第一輪 sparse 還領先。之後它一路往下掉到 27%，dense 那邊則穩定待在九成上下。

先講清楚這張表的份量：兩邊各只跑了一次，而且兩個 agent 面對同一個任務走了不同的
路徑，做了不同的工具呼叫。所以那個「dense 約 1676 秒、sparse 約 4404 秒」的
session 總時間差，不是一個可以引用的倍率。它只是讓我知道有東西壞了，值得去查。

## 我漏掉的那個變數

我量 prefill 的時候，量的是「這個請求花了多少時間」。

一個請求還會做另一件事：留下可以被重複使用的狀態。Dense prefill 算完整段 prompt，
結果寫回 prefix cache，下一個請求接著用。Sparse prefill 跳過了八成 token，算出來的
KV 是殘缺的——它可以正確地服務當下這個請求（打分挑出來的就是重要的 token），但它
不能被存起來，因為下一個請求會拿到一份有洞的歷史。

所以 sparse prefill 快，而且不留下任何東西。

單一請求的延遲數字看不見這件事。它只讀了其中一個座標軸。

## 崩塌

上面那張命中率表是觀察，不是機制。要看機制，我需要一條乾淨的軌跡：單一 server
process，只開 speculative prefill，沒有任何背景回填的程式碼在裡面競爭解釋。

拿到的是 20 次連續的 prefix cache 還原。

![一個 session，20 個請求](../figures/fig3-cache-cliff.svg)

藍色階梯是可重用的 checkpoint：28,672 往上走到 32,768、33,792、36,864、37,888。
正常。紅線是每個請求必須重算的未快取尾巴，一開始只有幾百到幾千個 token，也正常。

第 11 個請求，checkpoint 掉回 28,672。

然後它就停在那裡了。剩下的十個請求，藍線是一條水平線。紅線從 17,060 爬到 33,979。

伺服器日誌記下了那一刻的直接原因：

```
ArraysCache layer 0: partial prefix match detected (placeholder in last
matched block). Rejecting cache to prevent stale GDN state. Request will
reprocess from scratch.
```

Sparse prefill 在它沒算完的那個 block 裡留下一個 placeholder。Cache 層偵測到這個
placeholder，拒絕使用這份快取，以免把殘缺的狀態餵給下一個請求。

這個拒絕是對的。我不打算改掉它——改掉它就是拿正確性換延遲。但拒絕的代價是，最後
一份可信的 checkpoint 是 sparse prefill 開始之前那一份，而 context 還在繼續長。

Checkpoint 的寫入在 44,032 token 之後就完全停止。之後的十個請求，一次都沒有寫入。

## 債

我把那個瞬間叫 **cache cliff**：可重用的 dense checkpoint 落後於當前 context 的
那個事件。把之後累積起來、因為狀態再也回不來而必須不斷重算的部分叫
**prefix-cache debt**。

這兩個詞是我在這份研究裡定的，不是既有術語。我用它們是因為「cache 命中率下降」
這句話把一個會自我放大的過程講得太平了。

放大的部分在這裡：speculative prefill 的打分器本身要跑。它要掃過未快取的尾巴，
而尾巴正是債務的大小。

![打分成本隨尾巴成長](../figures/fig4-scorer-cost.svg)

從 8,535 個 token 花 2.7 秒，到 33,389 個 token 花 5.7 秒。這個優化的 overhead
跟著它自己製造出來的債一起長。

## 那能不能還？

想得到的第一個辦法：agent 在思考、在等使用者、在跑工具的時候，機器是閒的。用那段
閒置時間偷偷把 dense 版本補算回來，checkpoint 就能重新前進。

我用一個合成的互動式 workload 測了這個想法，參數是每一輪之間的閒置秒數。

![session 總時間對閒置時間](../figures/fig5-think-time.svg)

| 閒置 | dense only | hybrid |
|---:|---:|---:|
| 15 s | 108.7 s | 83.1 / 83.4 s |
| 10 s | 108.1 s | 84.5 s |
| 5 s | 108.1 s | 104.4 / 105.4 s |
| 0 s | 108.1 s | 119.7 s |

15 秒閒置的時候快 24%。5 秒的時候優勢基本消失。完全沒有閒置的時候，它比純 dense
慢 11%。

最後那一列才是這張圖的重點。回填要成立，回填的速度必須跑贏 context 的成長速度；
閒置時間不夠，回填就永遠追不上，而你還付了打分器的錢。任何只報「快 24%」而不附上
零閒置那一列的講法，是挑數據。

還有一種還債方式不需要閒置：讓 sparse 請求之後的下一個 dense 請求把缺口補回來。
在那 20 次還原裡，這件事一次也沒有成立——每一次的 sparse 節省，都小於後續補算所
需的重算量。這是對既有軌跡的觀察，我沒有另外跑一組強制插入 dense 請求的實
驗。

## 合成測試為什麼會誤導我

合成 workload 裡，每一輪 prompt 的成長是我自己設定的，成長速度溫和且穩定。閒置
時間也是我設定的。在那個世界裡，回填追得上。

真實的 coding agent 不長那樣。它讀一個檔案，整份內容一次塞進 prompt。它跑一次測
試，輸出再塞一次。成長是陣發的，而且工具呼叫密集的時候幾乎沒有閒置。同一個機
制，換一種 workload 幾何，結論反過來。

合成測試仍然有它的價值。它準確地找出了「回填速度必須跑贏成長速度」這個條
件——零閒置那一列早在真實 workload 之前就告訴我了。它做不到的是告訴我真實的成長
速度是多少。

## 第三種情況

如果故事停在「sparse prefill 在 agent session 裡是負的」，那也不對。

我後來量到另一個真實 agent，同樣只有一次 session：cache 命中率穩定在 84-86%，
最大的真實未快取尾巴約 2.5K，打分器呼叫次數是零。Speculative prefill 是開著
的，它從來沒有被觸發，因為 8192 的門檻從來沒有被跨過。Prefix cache 一直是健康
的，沒有東西需要被加速。

![三種情況](../figures/fig6-three-regimes.svg)

三種 workload，三個答案。一次性的長 prompt 冷請求，sparse prefill 完勝，因為沒有
後續請求會用到那份狀態，浪費掉的東西本來就沒有價值。持續延伸並撞上 cliff 的
session，它輸，而且愈跑愈輸。健康的漸進式 session，它不會被觸發，所以無關。

換句話說，答案取決於 workload 的形狀。這三個樣本各只有一次觀察，我不知道真實世界
的分布長什麼樣，只知道它不是單一答案。

## 一個比延遲更硬的問題

追這件事的過程中我發現了另一個問題，跟速度無關。

Speculative prefill 不能丟掉系統提示和工具定義——那些是必須被完整處理的。實作用
一個靜態的前綴邊界來保護它們，而那個邊界是用減法推出來的。有工具存在的時候，推出
來的邊界比真實邊界短，最少的一次只差 37 個 token。

那 37 個 token 是工具指令的尾巴和操作者自己的系統提示的開頭。它們落在允許被丟棄
的區域裡。

一個會改變受保護 prompt 語意的優化，不管它讓延遲降低多少，都是無效的。這個修正比
上面所有的延遲數字都重要，它以 oMLX PR
[#3756](https://github.com/jundot/omlx/pull/3756) 進了上游。

## 最後上線的是什麼

我把 speculative prefill 留著。它在冷啟動長 prompt 上的 3-4 倍是真的。

上線的是一條傳輸層策略：走 agent 的那條 API 路徑預設 dense，可以用單一請求參數
明確開啟 sparse；長 context 的那條路徑維持原本行為。沒有新的狀態，沒有分類器，
沒有自動路由。判斷交給呼叫端，因為呼叫端知道它自己是不是連續性的。oMLX PR
[#3762](https://github.com/jundot/omlx/pull/3762)。

我刻意沒有做自適應路由。要做那個，我得先能預測一個 session 會不會撞上 cliff，而這
份研究還沒有支撐那件事的證據。

## 所以

一個推論優化的成本，必須包含它為後續請求創造的——或沒有創造的——可重用狀態。單一
請求的延遲數字不包含這一項。

我還不知道要怎麼在請求進來的當下，判斷它屬於哪一種 session。
